Profilo GitHub

Panoramica

Ha progettato e implementato tutta la persistenza del progetto. Dal layer locale SQLite (11 tabelle, WAL mode, migrazioni idempotenti con backup pre-DROP) al layer cloud Supabase (schema PostgreSQL, Row Level Security, REST API client). È la base su cui poggia l'offline-first del gioco: il sistema funziona senza connessione, il cloud è un backup in sola scrittura.

Contributi per area

SQLite Locale

  • local_database.gd (394 righe) — facade SQLite via godot-sqlite GDExtension v4.7, delega a 9 repo modulari in autoload/database/
  • 9 tabelle di base: accounts, characters, rooms, inventario, sync_queue, settings, save_metadata, music_state, placed_decorations (piu' badges_unlocked e sync_dead_letter aggiunte dopo)
  • 4 indici sulle FK senza vincolo UNIQUE (i 4 duplicati degli autoindex UNIQUE rimossi nella 1.3.0); foreign_keys=ON fail-closed
  • PRAGMA journal_mode=WAL + foreign_keys=ON + busy_timeout=5000
  • BEGIN/COMMIT/ROLLBACK transaction pattern in _on_save_requested
  • CRUD completo per ogni tabella: upsert, get, update, delete, soft_delete

Migrazioni Schema

  • Migration 1: characters legacy senza character_id → backup characters_bak + inventario_bak pre-DROP (safety net rollback-safe)
  • Migration 2: ALTER TABLE accounts ADD COLUMN per display_name, updated_at, password_hash, deleted_at, coins, inventario_capacita
  • Migration 3: CREATE TABLE IF NOT EXISTS sync_dead_letter + accounts.failed_attempts / lockout_until_unix (lockout persistito)
  • Migrations idempotenti — si possono eseguire più volte senza errori
  • Logging strutturato di ogni step migration per debugging

Auth + Security

  • auth_manager.gd (418 righe) — guest + username/password (username case-insensitive, password con tetto 128)
  • PBKDF2-HMAC-SHA256 v4 (RFC 8018 §5.2) con salt per-account 16 byte, 100.000 iterazioni, chiave derivata 32 byte
  • Legacy hash migration: al primo login riuscito con un hash v1/v2/v3 si ri-hasha automaticamente a v4
  • Rate limiting persistito su accounts: 5 tentativi falliti → lockout 300s
  • Soft delete account (flag deleted_at) per audit trail
  • Integrazione is_open() check prima di ogni operazione DB (fix A26)

Supabase Cloud

  • supabase_client.gd (883 righe) — REST API client asincrono, oggi un client dormiente: nessun percorso di gioco lo attiva senza configurazione manuale
  • Schema cloud versionato (supabase/schema.sql): 5 tabelle PostgreSQL con RLS auth.uid() = user_id su ogni policy
  • 5 tabelle push live: profiles, user_currency, user_settings, music_preferences, room_decorations
  • Solo push: il cloud e' un backup del dispositivo, non una sincronizzazione fra dispositivi — il percorso di lettura non e' mai innescato
  • Session token cifrato con chiave derivata da device (ConfigFile.save_encrypted_pass) — fix B-019
  • HTTPS obbligatorio nella config validation (fix B-020)
  • Queue cap 500 per prevenire OOM (supabase_http.gd)
  • SQLite sync_queue persistente per retry offline
  • Graceful degradation su 404/400 relation error (schema evolving)

Data Mapping

  • supabase_mapper.gd — Single Point of Truth per il mapping dei campi local-to-cloud
  • Una sola direzione: profile_to_cloud, decorations_to_cloud, currency_to_cloud, settings_to_cloud, music_to_cloud. I mapper cloud-to-local sono stati rimossi (B-022) insieme alla pull sync mai implementata
  • .get(key, default) ovunque — missing field mai crash
  • supabase_config.gd — load config da user://config.cfg, validate url + anon_key

Data Integrity

  • HMAC-SHA256 save file validation design (architettura con Renan)
  • Atomic write pattern: temp file → rename per prevenire corruzione
  • Backup automatico prima di ogni save nuovo
  • Type validation ad ogni _apply_save_data (settings, music, inventory, character, pet, messes)
  • Mirror SQLite completo dalla 1.3.0: inventario popolato (chiavi id/qty), save_metadata scritta con slot e versione, il DB e' unico per i 10 slot
  • Clamping valori numerici: livello_stress 0-100, volume 0-1, capacita 1-999
